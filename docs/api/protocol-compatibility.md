# 协议兼容策略

> 文档状态：Current
> 权威范围：CLI/TUI 与 Core 的协议变更规则
> 维护触发：修改 JSON-RPC 方法、参数、结果、事件或错误

## 本文负责

- RPC、事件和错误契约的兼容与破坏性变更规则。
- CLI/TUI 与 Core 版本不一致时的维护原则。

## 本文不负责

- 不列出当前全部 RPC 或事件字段。
- 不承诺尚未实现的版本协商能力。


## 1. 当前兼容模型

当前 CLI 与 Core 由同一项目版本发布，协议没有独立版本号和协商机制。因此当前部署要求：

- CLI 与 Core 使用同一代码版本。
- 客户端不得依赖未写入 `docs/api/` 的内部字段。
- 服务端新增结果字段时，客户端应忽略未知字段。
- 请求参数使用严格模型，服务端会拒绝未知字段。

该策略适合当前本地单用户项目，但不能保证任意旧客户端与新 Core 兼容。

## 2. 兼容变更

通常可视为向后兼容：

- 新增 RPC 方法。
- 新增可选结果字段。
- 新增客户端可忽略的流式事件类型。
- 为错误 `data` 增加可选字段。
- 放宽不影响安全边界的字段限制。

即使兼容，也必须更新 API 文档和测试。

## 3. 不兼容变更

以下变更必须明确标记并同步升级所有客户端：

- 删除或重命名 RPC 方法。
- 修改必填参数、字段类型或语义。
- 删除结果字段或改变状态值含义。
- 修改 `agent.event` 终止规则。
- 修改错误码语义。
- 改变 token、Workspace 或 Session 身份规则。

当前没有正式版本协商，因此不兼容变更不得在未同步 CLI 的情况下发布。

## 4. 客户端实现规则

- 客户端生成 JSON-RPC `id`，但不得控制 `trace_id`、`run_id` 或 `execution_id`。
- 客户端必须匹配当前请求的 `request_id`。
- 客户端应忽略未知结果字段和未知非终止事件。
- 客户端必须将 `done`、`error` 和最终 JSON-RPC 响应视为不同层次的信息。
- 连接中断后不得自动重发非幂等请求，应先查询 `session.status`。

## 5. 未来版本化方向

引入独立前端发布后，协议应增加：

1. `core.capabilities` 或握手方法。
2. 协议版本与功能标志。
3. 明确的弃用周期。
4. 旧事件和字段兼容测试。
5. 客户端 SDK 或生成模型。

在这些能力实现前，[路线图](/docs/product/roadmap-and-known-limitations.md)将“无版本协商”作为已知限制。
